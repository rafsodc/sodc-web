# Current authorization, issued-token revocation and last-admin safety (#653/#654)

`UserSecurityState` is the server-owned authority for member/admin admission. Auth custom claims are a versioned mirror used as additional restrictive checks. A signed token cannot grant access by itself. Missing state denies member/admin access; request guards never bootstrap it.

## Enforcement and transition contract

Every protected client operation checks the caller's own state with `auth.uid`, redacts the lookup, requires `READY`, ready access, the same current profile status, an allowed membership status and an exact integer `securityVersion`. Admin operations additionally require `adminReady`. Mutations check before their writes within `@transaction`. Existing ownership and relationship checks remain. `docs/security/authorization-operations.json` inventories every operation; run `node scripts/check-authorization-inventory.mjs` to detect omissions.

Functions await `requireEnabled`/`requireAdmin` before protected work. Their fresh DB checks are cached only within that one request. Downstream role bypasses use the resulting effective permissions. Backend consumers use explicit `Service*` NO_ACCESS reads or existing service operations rather than relying on an absent `auth.uid` in the Admin SDK. The authorization connector uses a separate named Firebase App because installed Admin SDK 13.10 caches Data Connect instances without the connector ID. This prevents accidentally selecting the client API connector for security operations.

Staff-recipient selection and claimed sends also read fresh current security state, require ready matching profile/version eligibility and use `adminReady` for the admin bypass. Pending work never permits a send. Otherwise eligible pending synchronization or a READY authority with Auth-mirror drift is retryable: selection retains its UID and the delivery ledger retries with fresh scope, identity, version and email checks. Actual restriction, verification hold or scope revocation remains a terminal skip; a later grant never resurrects that skipped delivery.

The shared API is `functions/src/currentAuthorizationTransitions.ts`:

- `initializeUserSecurityState({userId, actorId, actorKind, actorSecurityVersion?, reason, operationId?, allowAdminBootstrap?})` is an explicit migration/bootstrap operation. Only a separately authorised bootstrap imports an existing Auth admin role. Ordinary guards cannot call it. Initial unverified identities receive a durable exact-address verification hold.
- `transitionUserSecurity({userId, actorId, actorKind, actorSecurityVersion?, reason, operationId?, membershipStatus?, admin?, authDisabled?, verificationEmail?, releaseEmailVerification?})` commits denied ready flags, the incremented version, target profile status and a durable `SecurityTransition` in one CAS transaction. An operation ID is bound to the complete normalized intent hash, not just an actor/reason. Reusing it for another action fails.
- `synchronizeUserSecurity(operationId)` resumes the stored intent. It mirrors claims/explicit account disable intent, verifies fresh Auth state, then conditionally makes that exact current version ready. A failed grant remains denied; an old worker cannot complete a newer state. A pending restriction remains effective even if Auth synchronization fails. Superseded pending operations are retired.

Both restrictions and restoration increment the version. `AdminSafetyControl("site-wide")` serializes all supported security intent mutations with a conditional monotonic control version. Its `readyAdminCount` equals the number of `adminReady` contributions. Begin atomically withdraws a ready target's contribution, clears ready flags, updates profile/version and inserts the immutable intent; it requires another ready administrator even when the eventual change preserves admin access. This includes active-to-active status edits, email reverification and supported account disable. Completion adds a contribution only after verified Auth synchronization of the matching pending intent. Grants are never counted while pending. Counter, state and intent changes commit or roll back together.

New interactive intents check the actual caller's current ready authority and signed security version inside that same control-serialized transaction. Clients supply a stable operation reference, never an actor/kind/version. ADMIN, SELF, SELF_VERIFICATION, OPERATOR and confirmed DRIFT have explicit service-owned boundaries. Background completion resumes the immutable intent authorized at begin, even after its original actor loses access; it does not authorize another intent or infer new privileges from the former actor. This policy prevents stranded durable work. Existing restricted-admin membership and resignation rules remain.

Explicit security changes that already match current authority produce a READY no-op receipt bound to the complete canonical request while retaining user readiness/version and original `state.operationId`. Routine verified sign-in without a hold repairs only the existing READY mirror; it creates no security receipt and does not require the global control to be READY. A no-op mirror repair can retry using its receipt; replay after a newer target version cannot undo it. Interactive retries reject superseded operations both before and after synchronization instead of reporting success; background retirement stays idempotent. Concurrent duplicate/uncertain writes reread the stored operation and compare actor, target, kind, flags, addresses and review evidence. Conflicts retry at most four times; no mutation is automatically replayed by the frontend. The operator CLI accepts a stable `--operation-id`; legacy imports derive stable IDs from the project/batch/source checksum/UID ledger.

Safety-reducing changes freshly verify the bounded current ready roster's profile and Auth eligibility and bind the evidence to the conditional control revision. More than 1,000 ready administrators or unresolved lookup/count drift refuses the change. Known external disable/delete/unverification is different: the account is already unusable. An audited DRIFT denial corrects its contribution, even to zero, without restoring Auth; zero sets `RECOVERY_REQUIRED`. Corrupt counted flags are also denied. A frozen operator recount records actual verified contributions and leaves BOOTSTRAP/RECOVERY_REQUIRED until separate activation. External raw Auth/SQL/IAM actions cannot share this database transaction and remain outside the prevention guarantee.

Email changes first bind a persistent hold to the intended new address and revoke current access; only then can Auth email be changed/unverified. A new PENDING applicant without security state gets an atomically denied, non-admin record and exact intended hold under current actor/control/profile guards. Concurrent approval either preserves that hold or wins first and forces the correction through the ordinary versioned transition; absence of a record never bypasses the hold. A concurrent reconciliation of the still-verified old email cannot release it. Before starting an Auth email write the endpoint rechecks that the exact denied hold still belongs to this operation (or its current-version no-op receipt); an obsolete completed operation cannot unverify a counted administrator again. Self reconciliation releases only an explicit hold after fresh Auth verification of the exact intended address, rechecking current profile/disabled state. It cannot generically enable a denied account. Initial/imported unverified accounts have the same supported verification recovery. Verified onboarding without a profile receives only its own fresh verified Auth email response; it never initializes a profile/security record or grants claims. The onboarding notification callable does not write custom claims; missing enabled/authority already denies access. Unheld restrictions require an authorised status/account transition.

The five-minute reconciliation scheduler retries pending intents and sweeps paginated existing states for READY Auth-mirror drift. Its handler performs no synchronization when the admin control is missing or BOOTSTRAP, including when a deployment creates its schedule before activation. Explicit operator work remains available during bootstrap. Existing READY/RECOVERY_REQUIRED reconciliation retains its normal repair semantics. A late old Auth write cannot change DB authority; the sweep or own-session check repairs its mirror using current authority. A known external disable/delete/unverified identity creates a new DB-first denial instead of undoing that restriction. External unverified identity denials bind the observed current email; other out-of-band restrictions require operator recovery. No Firebase Auth `onUpdate` mirror is assumed.

Completed sweeps log `pendingAttempts`, `stateAttempts`, `failedAttempts` and `durationMs`. Before promotion, measure a representative full roster and retry backlog in Dev/Beta, retain the roster size and execution evidence, and confirm sustained completion comfortably within both the five-minute cadence and the 540-second function limit. An absent completion log, timeouts or growing backlog fails this operational gate. Local unit timings do not establish production throughput; the current sweep is sequential and has no durable cross-invocation pagination cursor.

## Boundaries and recovery

The intentionally authentication-only callables are onboarding/display-name setup, pending-claim setup, email verification/reconciliation and `getMyAuthorizationStatus`. The latter accepts no target identity or permission flags and returns only `{status, isAdmin, securityVersion, tokenVersionCurrent, verificationRequired}` for the caller. `status` is `enabled`, `restricted`, `pending` or `missing`. It freshly reads own Auth/DB state; it may repair a READY claim mirror, but cannot bootstrap, start a grant, release a hold or return member data. It is rate limited to 30 requests per five minutes.

The frontend seam is `src/shared/auth/authorizationFailure.ts` plus the raw own-status wrapper `src/shared/auth/authorizationStatus.ts`. It recognizes the stable `SESSION_VERSION_STALE` and `ACCESS_REVOKED` markers through actual Error and Data Connect wrappers. #602 integration must mask private views immediately, capture/check its session generation around the status call, permit at most one forced refresh for a stale version and never replay a failed mutation automatically. `ACCESS_REVOKED` can also mean a pending synchronization or role-only admin denial. Do not blindly sign out an enabled member: pending remains masked with bounded retry; confirmed restriction/missing authority uses #602 sign-out cleanup; role-only loss refreshes claims and performs a controlled document reset to clear the installed SDK's private cache, returning to a safe member route.

An expected own-membership update captures its UID/session generation, cancels and fences prior private reads, and delays new reads while the one explicit write and token refresh finish. Follow-on profile/review writes proceed only after fresh own-status verification confirms current authority. A committed status with a failed refresh is reported as partial success and keeps private reads fenced until explicit retry/recovery. Concurrent account/role loss still hands off to normal recovery; no mutation is automatically replayed. Editing another user's status does not refresh the caller's token. Public bearer-capability queries retain their separate document boundary.

Public account recovery, signed guest capabilities and verified webhooks remain separate explicit boundaries. Section/file capabilities are issued only after current member and resource checks. An already-issued signed Storage URL remains usable until its expiry; version changes cannot recall it. Already-admitted work can complete after a subsequent restriction. The proposed release target is denial of newly started protected checks within **five seconds of the successful DB restriction commit**, measured with a retained signed token in non-production. This is a candidate release criterion, not an agreed operational SLA and not a promise for in-flight work or Console-only Auth changes.

Console-only Auth disable/delete and unsupported raw DB/Auth writes do not share this transaction. Use the supported service/operator path for immediate DB-first restrictions. Reconciliation detects known drift later, subject to scheduling, data volume, service availability and alert response; it is not an immediate external-change guarantee. Monitor failed/pending synchronization and READY mirror recovery warnings.

## One-time migration in each project

**Do not use the normal one-shot deploy before this migration.** The default checked-in connector is strict and denies old tokens/missing rows immediately. Old Functions also need the additive `Service*` reads before replacement. Rehearse each step in Dev, then Beta before Production. This runbook does not attest that a target project has completed the migration.

Use the [authorization migration tool workflow](./authorization-migration-tool.md) to prepare a project-bound run, review its gates and execute one checked phase at a time. `plan`, `prepare` and `status` are local operations; `audit` and `inspect` read live state; each confirmed cutover phase remains a separate action. The sequence below defines the underlying contract and the controlled operator procedures used by the tool. A failed or uncertain phase must not be bypassed by manually writing a migration receipt. The Dev backup waiver applies only to Dev; Beta and Production retain their resilience and recovery requirements.

1. Review the exact commit and backups, select the explicit project ID, and establish an **approved server-enforced security-write freeze**. Record the exact provider controls, affected entrypoints, operator and proof in the cutover evidence. For example, an approved provider invoker/IAM restriction can block the deployed security-writing callable services while separately authorized operator ADC access performs the migration; determine and approve the actual environment-specific controls first. Include role/status/resignation/email/Potential Lost writers, onboarding writers, own-status/READY mirror-repair entrypoints and verification reconciliation. Hosting maintenance or asking administrators not to click does not stop old tabs or direct requests. Verify and record that an old-tab/direct write request is refused by the server **before** changing connector signatures or activating the counter. Also pause pending/READY reconciliation jobs and migration writers, and wait for old in-flight writers to drain. Drain previously committed #653 pending intents using the reviewed old workflow before replacing connector signatures; retain their audit records. Keep the freeze through new Functions validation. Confirm that no scheduler or migration job still uses an Auth-only grant or legacy status writer.
2. For **every installation**, deploy the additive schema and authorization-service connector, keeping the existing API connector in place:

   ```sh
   firebase deploy --only dataconnect:sodc-web-service:schema,dataconnect:sodc-web-service:authorization-service --project sodc-web-beta
   ```

3. **Skip this compatibility step for an already strict #653 installation; never weaken an already strict connector.** For fresh/legacy installations only, prepare a new **local temporary source artifact**, explicitly project bound with expiry no more than 48 hours away:

   ```sh
   node scripts/prepare-authorization-rollout.mjs --project sodc-web-beta --output /tmp/sodc-authorization-beta-reviewed --expires <ISO-expiry-within-48h>
   ```

   Review `AUTHORIZATION-ROLLOUT.json`, the source diff and the expiry before using it. This command never deploys or changes default sources. Only this artifact omits the new current-state lookups; it retains all previous token/ownership checks, adds NO_ACCESS service operations, and removes SDK generation paths. It provides **legacy security only**, so the revocation target does not apply during this short frozen phase. From that temporary directory, deploy **only** `dataconnect:sodc-web-service:api` to the same explicit project. Never deploy the temporary artifact after strict cutover or after expiry. Expiry is operator enforced metadata, not an automatic cloud rollback timer.
4. Pre-create the control in a **separate committed operation**, before initializing/completing any new security state. A fresh installation starts BOOTSTRAP/count 0. An existing strict installation must first resolve known admin drift and drain old pending work; control creation verifies the entire existing ready roster in Auth/profile and atomically binds its count. Do not upsert-and-update a new control inside one transaction.

   ```sh
   npm --prefix functions run security-state-admin -- --project sodc-web-beta --all --mode control-create --apply --confirm-project sodc-web-beta --actor <operator-id> --reason <approved-cutover-reference> --operation-id <stable-create-control-reference>
   ```

   If new external drift appears after connector replacement and ordinary control creation refuses, do not roll back to unguarded online writes. Under the same approved server freeze, explicitly approve `--mode control-create-recovery` with its own stable reference. This creates **only BOOTSTRAP** from the actual DB ready-flag contributions and marks the creation audit `[OBSERVED_DRIFT_RECOVERY]`; it asserts no Auth usability and does not restore any account. Then run `control-recount`: it discovers deleted identities from the DB roster, DRIFT-denies definitively unusable rows and fails so the operator can review each correction. Repeat the same recount reference until all known drift is corrected; unknown lookup failures remain fail-closed BOOTSTRAP/RECOVERY_REQUIRED. Recover only specifically approved accounts through enable/exact verification release/grant, and activate separately after a full fresh verified audit. `repair --all` alone cannot find deleted Auth identities. A replayed creation reference performs no additional recovery work; the separate recount/repair/activation steps remain required.

   Audit/backfill existing Auth identities with membership profiles through the explicit CLI. Audit is read-only by default; output contains UID/classification only. Auth identities without profiles are skipped by bootstrap; onboarding remains available. Review orphaned profiles without an Auth identity separately and leave them denied until a supported identity repair. Do not infer a grant from the absence of an Auth account.

   ```sh
   npm --prefix functions run security-state-admin -- --project sodc-web-beta --all
   npm --prefix functions run security-state-admin -- --project sodc-web-beta --all --mode bootstrap --import-admins --apply --confirm-project sodc-web-beta --actor <operator-id> --reason <approved-migration-reference> --operation-id <stable-backfill-reference>
   npm --prefix functions run security-state-admin -- --project sodc-web-beta --all
   ```

   `--import-admins` is an explicit approval to adopt legacy roles, not a routine runtime repair. Review active profile eligibility, ready states, intended holds, pending/error records, mirrored versions and at least one verified non-disabled ready administrator. Use only the new CLI for controlled completion during the freeze, then rerun audit. Do not restart the old scheduler/writers. Never reset versions or overwrite authority from stale claims. This step invalidates old tokens; #602 recovery or explicit sign-out/sign-in is required.
5. Deploy new Functions against the additive API. Their awaited current guards are now strict. Immediately verify the security reconciliation job's actual paused/invoker-blocked state and deployed handler revision; do not assume a previously paused job covers a newly created schedule or another deployment. Keep the scheduler blocked until explicit activation. The new handler's missing/BOOTSTRAP guard is an additional cutover fence, not a substitute for the approved provider freeze or draining old invocations. Retain the job-state/refusal evidence before and after this deployment. Verify service reads, onboarding/approval, role/status transitions, exact-address verification, operator recovery, existing public/guest/webhook boundaries and current-recipient eligibility. Keep old writers frozen until all Functions instances/jobs use the new boundary. New code uses only isolated `ConfirmPotentialLostWithAdminSafety`, which checks current actor/control and atomically preserves evidence/profile/review audit. Older Potential Lost signatures belong only to the temporary migration compatibility artifact and never to a repair path.

   Activate only after fresh roster/profile/Auth verification and at least one ready admin, using a separate stable reference:

   ```sh
   npm --prefix functions run security-state-admin -- --project sodc-web-beta --all --mode control-activate --apply --confirm-project sodc-web-beta --actor <operator-id> --reason <approved-cutover-reference> --operation-id <stable-activation-reference>
   ```

   Resume only the new scheduler and lift the write freeze after all Functions use this boundary; deploy the new frontend with mandatory interactive operation references.
6. Deploy the strict API from the reviewed default checkout only after old Functions and in-flight writers have drained, then run the real signed-token gate and #602 recovery acceptance checks before Hosting promotion. Recheck that every eligible existing user has a versioned state and a refresh path. Strict sources exclude the legacy Potential Lost writers; verify direct legacy operation calls fail after cutover. Delete the temporary compatibility directory. Never restore migration-only signatures after strict cutover or use them as a repair path.
7. Record the one-time receipt at gitignored `.firebase/authorization-migration/<project-id>.json`:

   ```json
   {
     "schemaVersion": "sodc-authorization-migration/v1",
     "migrationId": "current-authorization-admin-safety/v2",
     "projectId": "sodc-web-beta",
     "gitSha": "<full-reviewed-migration-commit-sha>",
     "backfillComplete": true,
     "strictApiReady": true,
     "adminSafetyControlReady": true,
     "securityWriteFreezeVerified": true,
     "reviewedBy": "<operator-id>",
     "evidence": "<audit, strict API and non-production gate references>"
   }
   ```

   The normal deployment/preflight entry points require this project/epoch receipt and verify its recorded SHA is an ancestor of the requested revision before any remote step. It is a durable operator assertion with evidence, not an automated substitute for the audit. Descendant releases reuse it; the existing deployment preflight separately binds each exact release SHA. A #653-only `current-authorization/v1` receipt is rejected. The combined v2 epoch additionally requires explicit `adminSafetyControlReady: true` and `securityWriteFreezeVerified: true` evidence. The latter attests the approved provider controls and direct-refusal/drain evidence, not a Hosting-only notice; do not sign either assertion until the recorded gate passes. A fresh project, unrelated history or future migration epoch requires a new receipt. Keep receipt evidence in the approved operational record so another deploy host can verify/recreate it.

Rollback must preserve the schema/version rows and current authority. Prefer rolling back Hosting or fixing Functions while leaving strict API checks in place. Do not restore claim-only connectors, reset versions or restore an old Auth claim snapshot after cutover: that would re-enable retained tokens. An unavailable synchronization can be retried from the durable operation; an authorised compensating restoration is a new versioned transition.

## Operator restrictions and retries

Use `security-state-admin` with an explicit single `--user` for `--mode disable` / `--mode enable`, plus `--apply --confirm-project --actor --reason --operation-id`. Retry the exact same intent/reference after a transport uncertainty; use a fresh reference for a later deliberate action. Restriction commits denied state before Auth disable. Enabling checks the current profile, verified email and any hold before granting readiness. `--mode repair` resumes the current durable operation (or repairs its READY mirror), then records its own bound no-op receipt. It refuses missing authority and never invents a grant from Auth flags. `--mode bootstrap` is reserved for migration/new explicit bootstrap; existing state is not reimported from Auth. `--mode release-verification` explicitly releases a freshly verified exact-address hold. `--mode grant-admin` supports audited first-admin/operator recovery for an already initialized eligible member; `revoke-admin` uses ordinary last-admin protection. These modes require one explicit user. If external drift leaves zero, correct/recover the specific account through these explicit actions, use `control-recount` only under a frozen audited roster, and `control-activate` only after fresh verification/count agreement. Never automatically re-enable an externally disabled/deleted account. If the actual profile is restricted, enable/repair does not restore membership: use a separately approved already-eligible initialized member with grant-admin, or an explicitly reviewed OPERATOR transition restoring the approved membership status. A deleted/missing identity requires explicit approved identity repair before initialization/grant; never infer identity restoration from a counter deficit. Control creation/recount/activation are bound to durable full-intent audit receipts and independent references. Audit first and retain the UID-only result with the approval reference. Pending operations are also retried automatically. `cli-dev-reset` refuses before its first deletion if any control/security state exists or the guard lookup fails; use a reviewed offline fresh-project procedure instead. Its fresh-project-only seed explicitly creates/completes/activates the control. Raw Console or legacy role/status writers are never supported online bypasses.

## Validation and release evidence

Normal suites use deterministic unit/domain mocks and are not proof that Firebase accepted a retained signed JWT. The separate `functions/src/__tests__/users-auth/accessRevocation.integration.ts` uses the exact pre-change JWT bytes against deployed direct connector read/write operations and real callables. Raw Admin access is limited to unique `security-it-*` fixture setup, authoritative state observations, assertions and cleanup; it is not used as the proof of client authorization. It tests restriction/role revocation, no-write side effects, restoration/regrant and the proposed five-second denial criterion. Auth synchronization failures and stale-worker races are covered by unit/transaction tests, not by fault injection into live Auth.

The live suite requires an explicitly confirmed Dev/Beta project and site-wide Notify `SIMULATION` before fixture mutations. It never runs against Production or an emulator. Supply the target web API key through the approved environment mechanism:

```sh
RUN_SECURITY_INTEGRATION=1 SECURITY_INTEGRATION_PROJECT=sodc-web-beta SECURITY_INTEGRATION_CONFIRM=sodc-web-beta SECURITY_INTEGRATION_API_KEY=<target-web-api-key> npm --prefix functions run test:security-integration
```

If App Check is enforced on Auth/Data Connect, supply a valid target-project `SECURITY_INTEGRATION_APPCHECK_TOKEN` through the approved test attestation flow as well; do not weaken project enforcement to make the gate pass. The raw fixture Admin client explicitly selects the API connector so its cache cannot poison generated API operations.

The same command with `-- --check` checks targeting without network or account changes. Running without opt-in fails before network. This live gate has **not been executed** in this PR; it remains mandatory after a non-production deployment. Local Data Connect emulator smoke separately verified CEL/current reads and writes, denied-write rollback, restriction/restoration, stale-version/admin rejection and multi-connector service compatibility. Emulator impersonation does not replace the signed-token gate.
