# Organiser guests (#615)

Section moderators use **Administer → Organiser guests** and select an event. Administrators manage all three ticket categories in the existing event ticket-type table and editor: Member, Member’s guest, and Organiser/club guest. Section moderators use the Ticket types tab with the same table/editor limited to organiser allocations. The Guests tab manages people and links only. No personal member booking is needed.

The shared management UI combines the catalogues; `OrganiserGuestTicketType` remains a separate catalogue from member/accompanying-guest `TicketType`. Existing member booking and checkout APIs cannot resolve these IDs as eligible tickets. Organiser types support the same title, description, price, sort order and symposium/dinner settings. They do not use member access groups. Organiser types are archived rather than deleted; existing allocations cannot be converted between member and organiser categories. Guest records retain the allocated price and symposium/dinner flags when the catalogue is edited. Unpaid/complimentary guests can be reassigned to another active ticket for the same event, expiring old checkout and atomically updating their allocation. Once paid, changing allocation requires cancelling and adding a new reservation to preserve financial history.

An `OrganiserGuest` reserves one place immediately. The active count is the number of records without `cancelledAt`; payment, checkout expiry, and booking closure never change that count. There is currently no overall event capacity limit in the existing event model. This implementation contributes to attendee counts and does not introduce an arbitrary capacity limit or use a member's guest allowance.

All Data Connect operations are `NO_ACCESS`. Enabled section moderators or administrators manage guests through callables. User details, cancellation, dietary changes and link replacement use version checks and transactional audit entries. Creation uses a client-generated UUID so retrying a request cannot create another reservation. Concurrent duplicate creates may return an error; retrying the same UUID returns the existing reservation.

Guest links contain 32 random bytes in the URL fragment. Only SHA-256 hashes are stored. Links never expire automatically. A replacement changes the hash and checkout attempt key, preserving the guest and payment identity. The original plaintext link cannot be recovered: organisers copy it when generated, or replace it later. Treat the link as a capability and keep it private.

The public guest page bypasses membership/onboarding gates. Its capability permits reading that ticket, paying, and updating dietary requirements only. Dietary writes check the booking deadline both in the handler and atomically in Data Connect. Payment remains available after booking closes; the UI shows overdue status. Cancellation removes the guest from active attendance and prevents further guest writes and checkout creation.

Stripe Checkout uses the allocated amount in GBP and a stable attempt key. Card checkout is reused until complete or expired. An expired session receives a new attempt without releasing the place. Conditional attachment and token checks prevent an in-flight stale request from returning a usable new checkout after cancellation/link replacement. Existing open sessions are expired on cancellation/replacement. A payment that wins a cancellation race is recorded against the cancelled guest and shown as refund required. Signed webhook replay cannot replace an already recorded payment intent.

The existing signed `stripeWebhookPayments` endpoint handles guest session metadata before member payment routing. Guest payment/refund transitions use conditional database writes and audit entries. Refund events read Stripe's current refund list and distinguish succeeded from pending/failed refunds. No automatic refund policy or separate refund initiation is introduced; that work remains in #274. Keep `refund.updated` and `refund.failed` enabled alongside the events in the Stripe webhook runbook.

The public attendee list includes only names, guest classification and attendance flags. Organiser guests form a surname-sorted block after member booking groups because they have no attending member booker. Detailed guest exports are available to moderators; the administrator ticket report combines member and organiser tickets and waits for both data sources before export. Cancelled records remain in the management list but are excluded from attendee counts/exports.

Deployment requires the Data Connect schema/connector, Functions and frontend together. After deployment, verify a free guest, paid Stripe test checkout, payment after closing, dietary cutoff, link replacement, and cancellation/refund status with a real moderator. Unit tests mock Stripe/Data Connect and do not replace that integration walkthrough.
