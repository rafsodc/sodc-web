# Organiser guests (#615)

Section moderators use **Administer → Tickets and guests** and select an event. Administrators manage all three ticket categories in the existing event ticket-type table and editor: Member, Member’s guest, and Organiser/club guest. The organiser guest screen manages people and links only; there is no second ticket-type editor. No personal member booking is needed.

Organiser tickets are normal `TicketType` records with the `ORGANISER_GUEST` audience. They use the same access-group, title, description, price, sort-order, symposium/dinner, editing and deletion behaviour as member and accompanying-guest tickets. The standard event response removes this audience before the booking page receives it, and booking/payment callables reject it as a member booking line. Guest records snapshot the allocated price and symposium/dinner flags so later catalogue edits do not alter existing reservations. Existing guest tickets, including paid tickets, can be reassigned to another organiser ticket for the same event. This changes attendance inclusions and ticket title only: the original allocated price, checkout references and payment/refund records remain unchanged. Any financial adjustment is handled manually.

`OrganiserGuestTicketType` and the nullable legacy relation remain read-only for reservations created before this consolidation. No UI or callable can create or edit that legacy catalogue. Existing reservations continue to display their original ticket title while every new allocation references the standard `TicketType` relation.

An `OrganiserGuest` reserves one place immediately. The active count is the number of records without `cancelledAt`; payment, checkout expiry, and booking closure never change that count. There is currently no overall event capacity limit in the existing event model. This implementation contributes to attendee counts and does not introduce an arbitrary capacity limit or use a member's guest allowance.

All Data Connect operations are `NO_ACCESS`. Enabled section moderators or administrators manage guests through callables. User details, cancellation, dietary changes and link replacement use version checks and transactional audit entries. Creation uses a client-generated UUID so retrying a request cannot create another reservation. Concurrent duplicate creates may return an error; retrying the same UUID returns the existing reservation.

Guest links contain 32 random bytes in the URL fragment. Only SHA-256 hashes are stored. Links never expire automatically. A replacement changes the hash and checkout attempt key, preserving the guest and payment identity. The original plaintext link cannot be recovered: organisers copy it when generated, or replace it later. Treat the link as a capability and keep it private.

The public guest page bypasses membership/onboarding gates. Its capability permits reading that ticket, paying, and updating dietary requirements only. Dietary writes check the booking deadline both in the handler and atomically in Data Connect. Payment remains available after booking closes; the UI shows overdue status. Cancellation removes the guest from active attendance and prevents further guest writes and checkout creation.

Stripe Checkout uses the allocated amount in GBP and a stable attempt key. Card checkout is reused until complete or expired. An expired session receives a new attempt without releasing the place. Conditional attachment and token checks prevent an in-flight stale request from returning a usable new checkout after cancellation/link replacement. Existing open sessions are expired on link replacement. Attendance edits and deletion leave existing checkout sessions unchanged; deletion prevents new checkout creation. A payment that wins a cancellation race is recorded against the cancelled guest and shown as refund required. Signed webhook replay cannot replace an already recorded payment intent.

The existing signed `stripeWebhookPayments` endpoint handles guest session metadata before member payment routing. Guest payment/refund transitions use conditional database writes and audit entries. Refund events read Stripe's current refund list and distinguish succeeded from pending/failed refunds. No automatic refund policy or separate refund initiation is introduced; that work remains in #274. Keep `refund.updated` and `refund.failed` enabled alongside the events in the Stripe webhook runbook.

The public attendee list includes only names, guest classification and attendance flags. Organiser guests form a surname-sorted block after member booking groups because they have no attending member booker. Detailed guest exports are available to moderators; the administrator ticket report combines member and organiser tickets and waits for both data sources before export. Cancelled records remain in the management list but are excluded from attendee counts/exports.

Deployment requires the Data Connect schema/connector, Functions and frontend together. After deployment, verify a free guest, paid Stripe test checkout, payment after closing, dietary cutoff, link replacement, and cancellation/refund status with a real moderator. Unit tests mock Stripe/Data Connect and do not replace that integration walkthrough.

## Attendance-only edits (#633)

Both administrators and section moderators can edit existing member and accompanying-guest tickets, or confirm their deletion, without booking-window restrictions. The form changes the attendee display name (including accompanying guests), dietary requirements and ticket type within the same event and audience. Accommodation requests, accommodation notes and seating preferences are editable per ticket, including organiser guest tickets; editing one ticket leaves sibling preferences unchanged. Seating is entered as names, one per line (up to 20). Member tickets inherit the original booking preferences until explicitly overridden, and an empty override clears that preference. Reports and CSV exports include the per-ticket values. Organiser guest first and last names remain editable even after payment. It does not change a member profile or the original booking contact.

Member ticket corrections are stored on the stable `BookingPlace`: attendance ticket type, name, dietary note, accommodation/seating preferences, removed flag and a version counter. Original purchased `BookingLine` records and payment allocations are retained so existing balance calculations and transaction history do not change when a ticket is edited or removed. The edit mutation checks the active approved booking and attendance version atomically, recording the actor/time. Attendee lists, CSVs and member ticket displays apply these corrections. Removed places are omitted, including when every place in a booking has been removed; the original booking remains as purchase history. The event model has no overall capacity limit; reserved attendance counts derive from the remaining tickets.

Guest deletion uses the existing cancellation marker and retains its audit/payment records. Neither form initiates Stripe operations, creates financial adjustments or sends amendment emails. The confirmation explains that payments/refunds are handled manually. Already-open checkout sessions and incoming payment webhooks continue to represent the original purchase; a late guest payment after deletion remains recorded for manual reconciliation.
