# Organiser guests (#615)

Section moderators use **Administer → Organiser guests** and select an event. Administrators manage all three ticket categories in the existing event ticket-type table and editor: Member, Member’s guest, and Organiser/club guest. The organiser guest screen manages people and links only; there is no second ticket-type editor. No personal member booking is needed.

Organiser tickets are normal `TicketType` records with the `ORGANISER_GUEST` audience. They use the same access-group, title, description, price, sort-order, symposium/dinner, editing and deletion behaviour as member and accompanying-guest tickets. The standard event response removes this audience before the booking page receives it, and booking/payment callables reject it as a member booking line. Guest records snapshot the allocated price and symposium/dinner flags so later catalogue edits do not alter existing reservations. Guests can be reassigned to another organiser ticket for the same event, expiring old checkout and atomically updating their allocation. Paid replacements retain their original payment history: downgrades initiate the net refund and upgrades expose only the additional balance through the guest link. Unchanged tickets retain their allocated price.

`OrganiserGuestTicketType` and the nullable legacy relation remain read-only for reservations created before this consolidation. No UI or callable can create or edit that legacy catalogue. Existing reservations continue to display their original ticket title while every new allocation references the standard `TicketType` relation.

An `OrganiserGuest` reserves one place immediately. The active count is the number of records without `cancelledAt`; payment, checkout expiry, and booking closure never change that count. There is currently no overall event capacity limit in the existing event model. This implementation contributes to attendee counts and does not introduce an arbitrary capacity limit or use a member's guest allowance.

All Data Connect operations are `NO_ACCESS`. Enabled section moderators or administrators manage guests through callables. User details, cancellation, dietary changes and link replacement use version checks and transactional audit entries. Creation uses a client-generated UUID so retrying a request cannot create another reservation. Concurrent duplicate creates may return an error; retrying the same UUID returns the existing reservation.

Guest links contain 32 random bytes in the URL fragment. Primary links are stored only as SHA-256 hashes. Amendment emails have an additional capability whose hash authorises access; its plaintext link is retained in the server-only amendment outbox for reliable delivery. It is never included in organiser list responses or logs. Links never expire automatically. A replacement changes the primary hash and checkout attempt key and revokes every emailed amendment capability, preserving the guest and payment identity. Ordinary amendments preserve existing links. The original plaintext link cannot be recovered: organisers copy it when generated, or replace it later. Treat the link as a capability and keep it private.

The public guest page bypasses membership/onboarding gates. Its capability permits reading that ticket, paying, and updating dietary requirements only. Dietary writes check the booking deadline both in the handler and atomically in Data Connect. Payment remains available after booking closes; the UI shows overdue status. Cancellation removes the guest from active attendance and prevents further guest writes and checkout creation.

Stripe Checkout uses the allocated amount in GBP and a stable attempt key. Card checkout is reused until complete or expired. An expired session receives a new attempt without releasing the place. Conditional attachment and token checks prevent an in-flight stale request from returning a usable new checkout after cancellation/link replacement. Existing open sessions are expired on cancellation/replacement. A payment that wins a cancellation race is recorded against the cancelled guest and shown as refund required. Signed webhook replay cannot replace an already recorded payment intent.

The existing signed `stripeWebhookPayments` endpoint handles guest session metadata before member payment routing. Guest payment/refund transitions use conditional database writes and audit entries. Refund events read Stripe's current refund list and distinguish succeeded from pending/failed refunds. Organiser cancellation and downgrades initiate the applicable refund against the guest’s original payment sources. Refund failures remain visible and can be retried for active or cancelled guests without repeating the amendment. Keep `refund.updated` and `refund.failed` enabled alongside the events in the Stripe webhook runbook.

The public attendee list includes only names, guest classification and attendance flags. Organiser guests form a surname-sorted block after member booking groups because they have no attending member booker. Detailed guest exports are available to moderators; the administrator ticket report combines member and organiser tickets and waits for both data sources before export. Cancelled records remain in the management list but are excluded from attendee counts/exports.

Deployment requires the Data Connect schema/connector, Functions and frontend together. After deployment, verify a free guest, paid Stripe test checkout, payment after closing, dietary cutoff, link replacement, and cancellation/refund status with a real moderator. Unit tests mock Stripe/Data Connect and do not replace that integration walkthrough.

## Amendment notifications and recovery (#624)

Each edit or cancellation saves an immutable `OrganiserGuestAmendment` in the same transaction as the reservation update and audit entry. The dialog retains an amendment UUID across retries; a stored request hash prevents reusing that UUID for different changes. The outbox snapshots the recipient, before/after ticket details, prices and scoped link. All amendment queries and mutations require server access (`NO_ACCESS`).

After refund processing, the existing `bookingRevision` email template sends the change summary and current financial effect. Additional balances say “Payment required—please pay as soon as possible”; no reminder schedule or new deadline is created. Guest links do not require registration. Missing email addresses are reported explicitly so the organiser can deliver the link manually.

The existing notification delivery ledger deduplicates sends by amendment ID and recovers failed deliveries. Its scheduled recovery also scans old pending amendment outbox rows to cover a crash between saving the amendment and creating the delivery ledger. `Retry email` only retries delivery; `Retry refund` only reconciles the current guest balance. Neither creates another amendment. Notification recovery never restores a capability revoked by explicit link replacement.

Deploy the schema and regenerated connector before the functions/frontend changes. The outbox schema and new amendment mutations are additive. Previous mutation signatures remain available while older function instances finish during a rolling deployment.
